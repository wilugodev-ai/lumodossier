# LumoDossier on Render

The testing deployment has two Node web services in the same monorepo. The Next.js service hosts the website, sender dashboard and public signing screens. The NestJS service authorizes documents, talks to Supabase and private Google Cloud Storage, and processes jobs. Use the two HTTPS URLs Render assigns to these services. Reserve `lumodossier.com` for a later domain change. [Render web services](https://render.com/docs/web-services)

## Prepare the isolated test resources

1. Create a Supabase test project. Enable the email/password provider and copy the project URL and **publishable** key from the project dashboard. The browser and API use this same project for sender authentication. To test email confirmations with a mailbox outside the Supabase project team, configure Supabase Auth SMTP. A disposable, confirmed sender created through the Auth dashboard also works for testing password sign-in. [Supabase API keys](https://supabase.com/docs/guides/api/api-keys) · [Supabase Auth email](https://supabase.com/docs/guides/auth/auth-smtp)
2. Under **Connect**, copy the database connection URI. Use a direct connection when the host has IPv6 connectivity, or the IPv4 session pooler on port 5432. Percent-encode special characters in its password. Enable SSL enforcement and download the project CA in PEM format under database settings. Supply its base64 encoding in `DATABASE_CA_BASE64` on Render. Alternatively configure `DATABASE_CA_FILE` with the path to a PEM file for local migration commands. These settings enable CA and hostname verification. Omit `sslmode`, `sslcert`, `sslkey` and `sslrootcert` from the URI when using them, because node-postgres replaces the configured TLS object if those query parameters are present. [Supabase PostgreSQL connections](https://supabase.com/docs/guides/database/connecting-to-postgres) · [TLS verification](https://supabase.com/docs/guides/platform/ssl-enforcement) · [node-postgres TLS configuration](https://node-postgres.com/features/ssl)
3. From the repository root, install the locked dependencies and run `pnpm migrate` against this project before serving requests. Set `MIGRATION_DATABASE_URL` to the schema owner's connection for this command. The migration creates the `lumo_service` group. For the API and job runner, create a dedicated database login with `NOINHERIT NOBYPASSRLS`, assign its password securely, and run `GRANT lumo_service TO your_runtime_login` as the migration administrator. Set the runtime `DATABASE_URL` to that login's connection. On the shared pooler, the user field has the form `your_runtime_login.project_ref`. Each application transaction assumes the service role. Apply the checked-in additive migrations with each release and keep migration credentials in the release environment.
4. Create a dedicated test GCS bucket. Enable **uniform bucket-level access** and **public access prevention**. Create an API service account and grant it **Storage Object User** on this bucket. Set `GCS_BUCKET` to its name. Base64-encode the service account's JSON credentials as a single value and place them in Render's API secret `GCS_CREDENTIALS_BASE64`. Base64 is an encoding, so retain the same protection and rotation practices as for the original private key. The frontend needs only the signing API URL to fetch documents. [GCS access control](https://docs.cloud.google.com/storage/docs/access-control) · [Storage IAM roles](https://docs.cloud.google.com/storage/docs/access-control/iam-roles) · [Service account key management](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys)

## Create the two services

1. Make the project, including `pnpm-lock.yaml` and `render.yaml`, available to a Git provider connected to the **testing** Render workspace. Select **New → Blueprint**, select the repository and test branch, and review the proposed services. Keep the repository root as the build directory so both packages can access workspace dependencies. The Blueprint uses Node 24.19.x and Corepack uses the pnpm version in the root `packageManager` field. [Blueprint reference](https://render.com/docs/blueprint-spec) · [Monorepo builds](https://render.com/docs/monorepo-support) · [Node version selection](https://render.com/docs/node-version)
2. Enter the test project's Supabase URL and publishable key under the web service. Enter the runtime database connection, encoded database CA, private bucket name and its encoded credential under the API service. Render generates a stable, random `LINK_SECRET` for the API. Preserve it across deployments and job runners. Render prompts for `sync: false` values during initial creation. To change them later, use the appropriate service's **Environment** page.
3. Sync the Blueprint. Record the **public HTTPS URLs** assigned to both services. Before testing, add `NEXT_PUBLIC_API_ORIGIN` to the **web service**, with the API's assigned public origin, and select **Save, rebuild, and deploy**. Next.js embeds `NEXT_PUBLIC_*` variables during its production build. A change to any public variable needs a new frontend build. The API receives its `WEB_ORIGIN` and public Supabase configuration by referencing the web service. For a connected CRM, use the same isolated Supabase issuer and database as the Touchlumo test deployment, set `TOUCHLUMO_ENABLED=true`, and add the CRM's exact HTTPS testing origin as `CRM_ORIGIN` on the API. CRM reads go through PostgREST with the sender's verified session and its workspace policies. Use origins without trailing slashes. [Next.js environment variables](https://nextjs.org/docs/app/guides/environment-variables) · [Render service configuration](https://render.com/docs/configure-environment-variables)
4. In the test Supabase project, set **Authentication → URL Configuration → Site URL** to the frontend's assigned HTTPS origin. Add that exact origin followed by `/dashboard` to the redirect allowlist. Add `http://localhost:3000/dashboard` when testing this same project locally. A separate Touchlumo test frontend should have its own exact callback registered when it handles authentication. [Supabase Auth redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)
5. Check the following commands and paths on the deployed services. Their start scripts listen on `0.0.0.0` and consume Render's `PORT`. Use the assigned API and frontend URLs to request `/health` over HTTPS and confirm each returns a success response before running the workflow below. [Render port binding](https://render.com/docs/web-services#port-binding) · [Render health checks](https://render.com/docs/health-checks)

| Service | Build after installing from the workspace root | Start | Health |
| --- | --- | --- | --- |
| Next.js frontend | `corepack pnpm --filter @lumo/web build` | `corepack pnpm --filter @lumo/web start` | `/health` |
| NestJS API | `corepack pnpm --filter @lumo/api build` | `corepack pnpm --filter @lumo/api start` | `/health` |

The deployment secret store supplies credentials at runtime. Supabase holds workflow state, evidence, link hashes and pending jobs. GCS holds the private document files. An API restart or a replacement Render instance reconnects to those same resources.

## Email invitations and completion messages

Manual sharing works with `EMAIL_API_KEY` and `EMAIL_FROM` unset. To enable the HTTPS email adapter, verify a sending domain in Resend, publish its requested DNS records, create a sending-only key for the domain, and set `EMAIL_API_KEY` and `EMAIL_FROM` on the API. Use a sender such as `LumoDossier <signatures@YOUR_VERIFIED_DOMAIN>`. The default endpoint is `https://api.resend.com/emails`. To use a compatible provider, set `EMAIL_API_URL` to its HTTPS endpoint and confirm it supports the adapter's request, response and idempotency conventions. The sender also needs access to the configured domain. [Resend verified domains](https://resend.com/docs/dashboard/domains/introduction) · [Resend API keys](https://resend.com/docs/dashboard/api-keys/introduction) · [Send email](https://resend.com/docs/api-reference/emails/send-email)

Use disposable addresses that you control for a real-provider smoke test. Keep click tracking disabled on the sending domain so the provider leaves private invitation links intact. The application's email attempt status describes the handoff to the provider. Use the provider's own events to investigate bounces and mailbox delivery. Supabase sender-account confirmation mail uses its separately configured Auth mail service. Set its sender name and confirmation template to LumoDossier for the standalone deployment. [Resend link tracking](https://resend.com/blog/open-and-click-tracking)

## Durable processing and cold starts

The Blueprint uses two Free test web services with `JOBS_INLINE=true`. The API processes pending database jobs while it is running. Render can spin down a Free service after 15 idle minutes or restart it. Work that comes due while the API is asleep waits for the next active run. A cold start adds latency to a sign-in, preview or signing submission. Check status after reconnecting and allow the queued work to finish. Render, Supabase, Cloud Storage and the email provider each have separate usage limits and potential charges. [Render Free limitations](https://render.com/docs/free)

For background progress during idle periods, create a **paid Render Cron Job** in the same testing project from the same Git commit. Use the API's build command in the Blueprint, including its install step, then set the run command to `corepack pnpm --filter @lumo/api jobs`. A schedule such as `*/5 * * * *` runs every five minutes in UTC. Supply the **same** API environment, including database CA, bucket credentials, public frontend origin and link secret. A bounded run claims due jobs from PostgreSQL and exits. Set `JOBS_INLINE=false` on the API if the cron service should handle all processing. Render bills cron separately under its current plan terms. [Render Cron Jobs](https://render.com/docs/cronjobs)

## Smoke test and domain changes

1. Sign in as a disposable sender. Upload a small, two-page PDF with no customer information. Add two disposable recipients in sequential order, place their fields and save the draft. Reopen the draft and check both pages.
2. Send the request. In manual mode, obtain the first recipient's link in request details and open it in a private browser. Read the consent, fill the fields and explicitly confirm signing. Check the sender's recipient timestamps and partial progress, then repeat for the second recipient in another private session.
3. Wait for completion processing. Download the completed PDF and completion record as the sender, then download the recipient copy through its secure link. Check placements, both names, server timestamps and hashes. Check the same request through the connected Touchlumo test workspace when its integration is installed.
4. Restart the test API service with a queued job or saved draft, open its HTTPS health URL and repeat the status or download check. Exercise an expired or cancelled request in a private session and confirm access is rejected. Record the actual Render URLs, outcomes and any delivery failures in release notes.

When the custom domain is ready, attach the domain on Render, update the Blueprint's `WEB_ORIGIN` to the new public frontend origin, update Supabase's Site URL and redirect allowlist, and rebuild the web service if the API origin changes. Keep previously issued invitation URLs reachable for their remaining validity period. [Render custom domains](https://render.com/docs/custom-domains)
